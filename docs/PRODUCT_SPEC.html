1 · Executive Summary

Nex Order (internally also referenced as the AYAM Order System) is a B2B order-management web application that lets restaurant and hotel customers (HoReCa) place orders for AYAM-brand Asian food products, sales reps place orders on their customers’ behalf, and a back-office team manage the catalogue, accounts, and field operations that surround that order flow.

The application is a single-page React 19 + TypeScript app served from Vercel (nexorder.vercel.app), with all state of record living in a Supabase Postgres database. The architectural shape is deliberate: every privileged write goes through a Deno Edge Function rather than direct database access. Row-Level Security on the underlying tables is configured to revoke INSERT/UPDATE/DELETE from the authenticated role for everything that matters, so a compromised browser session cannot bypass the validation, role gates, audit logging, or rate limits that the Edge Functions enforce.

The system has five roles — Admin, Manager, Field Sales Rep, Office Sales Rep, and Customer — and supports the full B2B distribution loop: catalog browsing, tier-aware pricing, multi-format promotions (percentage, fixed-price, BOGO, bundle, clearance), cart with delivery scheduling, an authoritative place-order path that runs stock and credit checks atomically, an order-status state machine, accounts-aging with order blocking, supplier and purchase-order management, sales targets with dashboards, route planning with check-in / visit logging for field reps, walk-in customer onboarding, transactional email scaffolding, real-time subscription updates, and a complete audit trail of every privileged mutation. The codebase has roughly 50 user-facing components across 16 functional epics, 13 deployed Edge Functions, and 16 numbered Postgres migrations.

What this document does, and what it does not

This document is a dev-team handoff artifact. Its goal is that a new engineer can read it cold and understand the entire system — what each role can do, what flows exist, what is shipped, and what is left. It is not a marketing brochure: section 6 lists every known production gap, including six new issues uncovered while preparing this document. Where there is a tension between honesty and polish, this document errs toward honesty.

The document does not include API contracts, database column specifications, or per-component prop tables — those live next to the code. It does include enough file paths and Edge Function names that any claim made here can be verified in source within seconds.

2 · Roles & Capabilities

2.1 Role descriptions

Admin

The platform owner. Has unconditional access to everything: catalog management, customer (HoReCa) creation and deletion, promotion design, supplier and purchase-order management, user provisioning, app-wide settings (currency, low-stock thresholds, payment-blocking limits, blanket discounts), and the audit log of every mutation in the system. Admins can edit a HoReCa’s sensitive fields (credit limit, tier, discount percent) without justification — the reason-prompt gate applies only to Managers.

Manager

A back-office user who runs day-to-day operations but does not own platform configuration. Managers can advance order status through the state machine, manage the product catalog, manage HoReCas (with a mandatory 5–500 character reason attached to any change of credit limit, tier, or discount), manage suppliers and purchase orders, set sales targets for reps, and approve or reject route plans submitted by field reps. Managers cannot invite users, edit app settings, view the audit log, or modify promotions on the same level as Admin (in practice promotion CRUD is also gated to Admin+Manager at the Edge Function, but the UI surface for promotions sits in the Admin tab tree).

Field Sales Rep

A mobile-first user who is out visiting customers in person. Has the same shopping interface as a Customer but can switch between any of their assigned HoReCas to place an order on their behalf. Owns route planning — creating a multi-stop visit list, optimising the order, starting the route, checking in at each stop, logging visit outcomes (Order Placed, Follow-up, Not Available, No Interest, Stock Check), and capturing photos and competitor notes. Sees a dashboard tuned for their personal performance: own revenue, AOV, target progress, at-risk customers, and reorder predictions.

Office Sales Rep

A desk-bound counterpart to the field rep. Same shopping and order-history capabilities, same dashboard, but no route planning, no scheduled visits, and no walk-in review — this role exists for inside-sales staff who take phone orders or work the order pipeline without doing physical site visits.

Customer (Restaurant/Hotel)

The end customer — a restaurant, hotel, or other HoReCa that buys from the brand. Self-service ordering only: can browse the catalog, build a cart, manage their own pantry of frequently-ordered items, reorder from any of their past orders, see their own delivery and invoice history, and view their own outstanding balance. Cannot see other customers’ data, cannot manage anything, and cannot place an order if their account is blocked for being over the payment threshold.

How the matrix is enforced. Every mutate-* Edge Function calls requireAuth(req, { allowedRoles: […] }) on entry. If the JWT’s profile.role is not in the allowlist, the function throws a structured FORBIDDEN (HTTP 403) before any work happens. Migration 00013_lockdown_admin_mutations.sql additionally REVOKEs direct INSERT/UPDATE/DELETE on the underlying tables from the authenticated Postgres role, so even a malicious browser cannot bypass the function.

4 · End-to-End Use Cases

Eight critical flows, written as numbered steps with role + screen labels, in the order they would typically run during QA. Each step references the screen or component a tester is on at that moment.

UC-1 · Customer self-service order

  1. [Customer]Sign in at /; AuthGate resolves the role from profiles and routes to ShopView with the customer’s own HoReCa pre-selected.
  2. [Customer]Browse the catalogue, optionally filter by category, and click Add on a product card. Quantity and pack-size are confirmed; cart updates in OrderContext.
  3. [Customer]Open the cart panel; review applied promotions, choose a delivery date and time slot, add notes.
  4. [Customer]If outstanding balance exists, the alert displays. If the account is blocked, the submit button is disabled.
  5. [Customer]Click Submit; OrderVerificationModal shows items, total, HoReCa, delivery info.
  6. [client → server]place-order runs auth, scope check, stock check (optimistic-locked), credit check, minimum-order check; on success inserts orders + order_items + invoice and decrements inventory.
  7. [server]place-order fires a fire-and-forget POST to send-email with template order_confirmation; failure is logged and does not roll back the order.
  8. [Customer]OrderConfirmation modal shows order ID, total, delivery date, status. Realtime subscription pushes the new row into OrderHistory.

UC-2 · Field rep places order on behalf of a HoReCa with a promotion applied

  1. [Field Rep]From HoReCaListView click Start Order on the customer; handleStartOrder seeds OrderContext.selectedHoReCaId.
  2. [Field Rep]Add products; PromotionsBanner shows that a BOGO is active for one of the categories.
  3. [Field Rep]Once the BOGO trigger threshold is hit, BundleSelectModal opens to pick the free secondary item; selection writes back into the cart line.
  4. [Field Rep]Submit; same place-order path as UC-1, but the JWT identifies a Field Rep so the server allows any HoReCa.
  5. [Customer]Receives the same realtime order-status updates and confirmation email path.

UC-3 · Reorder from past order (single + bulk merge/replace)

  1. [Customer]Open OrderHistory; expand a past order; click Reorder.
  2. [Customer]handleReorder populates the cart; unavailable items are flagged in the Unavailable panel.
  3. [Customer]Choose Merge (add to existing cart) or Replace (overwrite cart). Adjust quantities.
  4. [Customer]Bulk reorder: select multiple past orders via the table’s checkbox column, click Reorder selected; the same merge/replace prompt appears.
  5. [Customer]Continue to checkout as in UC-1.

UC-4 · Pantry — add, edit, bulk-add, OOS substitute

  1. [Customer]Switch to the Pantry tab in OrderingTabBar; the list reflects rows from pantry_items filtered to the active HoReCa.
  2. [Customer]Click Add to pantry on a product; PantryAddDrawer sets default quantity (pre-filled from last-ordered quantity) and optional preferred pack size.
  3. [client → server]mutate-pantry-item validates pack size against products.carton_size, persists, audit-logs.
  4. [Customer]If a pantry item is out of stock, the row shows the warning; click opens PantrySubstitutePopover with suggestions; pick one to swap into the cart this time only.
  5. [Customer]Bulk-select multiple pantry rows; Add selected to cart; quantities default to the saved pantry quantity.

UC-5 · Field rep plans a route, starts it, checks in, logs a visit

  1. [Field Rep]Open Scheduled Visits; click New Route; pick a date.
  2. [Field Rep]ScheduledVisitWizard: search-and-add HoReCas as stops; drag to reorder; review map; save.
  3. [Field Rep]Submit for approval; route enters Admin’s approval queue.
  4. [Field Rep]On the day, open the route from the Today tab; click Start route.
  5. [Field Rep]Arrive at first stop; click Check in; VisitModal opens with outcome chooser, notes fields, photo upload, next-visit recommendation.
  6. [Field Rep]Submit visit; stop status flips to Visited; departure time is captured.
  7. [Admin]The completion percentage on the tracking map updates in real time via the realtime subscription.

UC-6 · Admin approves a rep-submitted route and tracks completion

  1. [Admin]Open Scheduled Visits tab; click into Approval Queue; review the rep’s draft route.
  2. [Admin]Click Approve; rep is notified via NotificationPanel.
  3. [Admin]On execution day, open Tracking Map; see live stop status across all reps.
  4. [Admin]Drill into ScheduledVisitTrackingDetail to see per-stop dwell time and visit outcomes.

UC-7 · Manager edits a HoReCa’s tier — reason gate → audit entry

  1. [Manager]Open HoReCaForm for an existing customer; change tier from Silver to Gold.
  2. [Manager]Save; the form intercepts: a 5–500 char reason is required because tier is in SENSITIVE_FIELDS and role is Manager.
  3. [client → server]mutate-horeca updates the row, then logAuditEvent writes {action: 'update', resource: 'horecas', before, after, reason} to audit_events.
  4. [Admin]Open Audit Log; filter by resource = horecas, action = update; expand the row to see the diff and the reason text.

UC-8 · Admin reviews aging, blocks an over-limit customer; subsequent order attempt is rejected

  1. [Admin]Open Accounts; sort the aging table by 90+ bucket descending.
  2. [Admin]Drill into the top customer; review their unpaid invoices.
  3. [Admin]Open the customer’s HoReCa profile; toggle the block flag (or rely on the configured payment-blocking threshold).
  4. [Customer]Attempts to place a new order; OutstandingPayments surfaces the alert at checkout; place-order rejects with HTTP 422 CREDIT_EXCEEDED.
  5. [Customer]Sees a clear error and a CTA to settle the outstanding amount.

Architectural takeaway. Twelve of the thirteen functions follow this pattern; place-order is the only one missing the audit log call (see § 6.2 AUDIT-1).

6.2 Newly identified during this audit

The following items surfaced while preparing this document and are not in CLAUDE.md. They have been verified in source.

IDSeverityIssue & locus
AUDIT-1 HIGH place-order does not call logAuditEvent() after a successful order insert. Every other mutation Edge Function (mutate-horeca, mutate-product, mutate-promotion, mutate-supplier, mutate-purchase-order, mutate-sales-target, mutate-app-settings, mutate-pantry-item, update-order-status, invite-user) writes to audit_events. Order creation does not, which means the audit trail has a hole around the most-frequent privileged write in the system.

Fix: call logAuditEvent with {action: 'create', resource: 'orders', resourceId, after: orderSnapshot} after the order insert succeeds.
Locus: supabase/functions/place-order/index.ts ~line 354.
AUDIT-2 HIGH Three direct DB writes in services/supabase/horecaService.ts bypass Edge Functions. markHoReCaReviewed (lines 53–66), upsertHoReCaPricing (lines 68–83), and deleteHoReCaPricing (lines 85–92) call supabase.from('horecas').update and supabase.from('horeca_pricing').upsert/delete directly. These bypass role-gating, validation, and audit logging entirely. Migration 00013 currently REVOKEs those table permissions from authenticated, so in production these calls fail at the RLS layer — making them either dead code or silently broken UI affordances.

Fix: introduce mutate-horeca-pricing + mutate-horeca-review Edge Functions (or extend mutate-horeca with new action variants) that gate by Admin/Manager role, audit-log, and replace these direct calls. Then verify the UI surfaces that depend on these are still reachable, or remove the dead code.
Locus: services/supabase/horecaService.ts lines 53–92.
AUDIT-3 MED RESEND_API_KEY not yet set in Supabase secrets → send-email returns { ok: true, sent: false, reason: 'not_configured' } silently. The system is functioning correctly by design (orders should not block on email outage), but the operational reality is: today no order or invoice email is being sent. Operator runbook: npx supabase secrets set RESEND_API_KEY=re_… EMAIL_FROM='Nex Order <orders@…>'. (Already in CLAUDE.md backlog item 3, restated here so the audit context is in one place.)
AUDIT-4 MED mutate-promotion accepts targeting.kind = 'rep' with arbitrary repUserId but does not verify the user exists or has a sales-rep role. A typo in admin entry creates a promotion that targets a non-existent user; nothing fails until query time, and the failure is silent (no matches).

Fix: add a profile lookup in the Zod refinement step; reject if profile missing or role not in [‘Field Sales Rep’, ‘Office Sales Rep’].
Locus: supabase/functions/mutate-promotion/index.ts.
AUDIT-5 LOW Rate limiter is per-isolate / in-memory only. Counters reset on cold start; warm isolates do not share state. This is fine for v1 (it stops simple bursts) but is not a true global cap. (Backlog item 8 covers the same issue from the operator side; restated as an audit row so the cross-reference is clear.)
AUDIT-6 LOW place-order rollback on inventory race is best-effort. If the optimistic-lock UPDATE fails (concurrent decrement), the function tries to DELETE the order + items it just inserted. Supabase-js has no transactions, so a partial DELETE failure could leave a phantom invoice referencing an orphaned/deleted order. Watch for this pattern in production logs; if observed, hoist the whole flow into a Postgres function with a true transaction.
Locus: supabase/functions/place-order/index.ts.
